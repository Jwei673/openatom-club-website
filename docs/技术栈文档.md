# 电子科技大学成都学院开放原子开源社团官网系统技术栈文档

版本：v0.2  
项目类型：社团官网 + 内容社区 + 后台管理系统  
前端技术栈：Vue 3 + TypeScript + Vite  
后端技术栈：Spring Boot 3 + Spring Security + JWT + MyBatis-Plus  
数据库：PostgreSQL  
后续兼容方向：OpenTenBase  
部署方式：云服务器直接部署  
后端架构：模块化传统分层架构 + 少量 DDD 思想  

---

## 1. 技术选型目标

本项目不是单纯静态官网，而是包含官网展示、用户登录、角色权限、部门组织、内容发布、内容审核、活动报名签到、项目展示、积分记录、通知系统、操作日志和后台管理的综合系统。

技术选型目标：

```text
1. 适合 AI 辅助开发
2. 适合本人理解、测试和验收
3. 适合后续社团成员接手维护
4. 适合正式上线部署
5. 适合权限、审批、后台管理等复杂业务
6. 数据库设计尽量兼容后续 OpenTenBase 研究方向
```

---

## 2. 总体技术栈

本项目采用前后端分离架构。

```text
前端：Vue 3 + TypeScript + Vite
后端：Spring Boot 3 + Spring Security + JWT + MyBatis-Plus
数据库：PostgreSQL
后续数据库兼容方向：OpenTenBase
部署：云服务器 + Nginx + Spring Boot Jar + PostgreSQL + systemd
架构：模块化传统分层架构 + 少量 DDD 思想
```

不采用：

```text
Vue 2
完整 DDD
微服务
纯静态网站
localStorage 模拟正式数据
第一版强制 Docker 部署
```

### 3.2 选型说明

使用 Vue 3，而不是 Vue 2。

原因：

```text
1. Vue 3 是当前主流 Vue 版本
2. 生态成熟，学习资料多
3. 适合开发官网、成员中心和后台管理系统
4. 与 TypeScript 配合较好
5. 后续社团成员较容易接手
```

使用 Vite 作为构建工具。

原因：

```text
1. 启动快
2. 配置简单
3. 适合 Vue 3 项目
4. 开发体验好
```

使用 TypeScript。

原因：

```text
1. 数据结构更清晰
2. 减少低级错误
3. 接口类型更容易维护
4. 方便 AI 生成和检查代码
```

## 4. 前端页面分层

前端页面分为三类。

```text
1. 官网前台
2. 登录后的成员社区
3. 管理后台
```

### 4.1 官网前台

面向游客、学校老师、外部社区和潜在加入者。

页面包括：

```text
首页
关于社团
新闻动态
活动展示
项目展示
知识库
友情链接
加入我们
```

设计要求：

```text
1. 页面美观、大气、有科技感
2. 参考比赛第一名作品 Organization-Blog 的前端视觉风格
3. 首页只展示精选内容
4. 不把后台管理功能堆到首页
5. 适配 PC 和移动端
```

### 4.2 成员社区

面向登录后的普通成员。

页面包括：

```text
个人中心
成员主页
帖子列表
帖子详情
发帖页面
评论
活动报名
积分记录
站内通知
```

要求：

```text
1. 信息密度适中
2. 交互清晰
3. 保持与官网前台一致的设计语言
4. 根据权限显示或隐藏按钮
```

注意：

```text
前端隐藏按钮只是体验优化，不能作为安全依据。
真正的权限必须由后端校验。
```

### 4.3 管理后台

面向干事、副部长、部长、副会长、会长。

页面包括：

```text
后台仪表盘
用户管理
部门管理
权限管理
内容审核
新闻管理
活动管理
项目管理
文件管理
系统配置
操作日志
```

要求：

```text
1. 使用侧边栏 + 顶部栏布局
2. 清晰、稳定、高效
3. 不追求过度炫酷
4. 根据权限显示不同菜单
5. 无权限访问时显示 403 页面
```

## 6. 后端技术栈

### 6.1 核心技术

```text
Spring Boot 3
Spring Security
JWT
MyBatis-Plus
Spring Validation
Spring Boot Actuator
Lombok
```

### 6.2 Spring Boot 3

后端使用 Spring Boot 3。

原因：

```text
1. Java 后端主流技术栈
2. 适合权限、审批、后台管理、日志等复杂业务
3. 学习资料和社区资源多
4. 便于答辩解释 Controller、Service、Mapper、Entity 等结构
5. 适合打包成 jar 部署到云服务器
```

### 6.3 Spring Security

Spring Security 用于认证和权限控制。

主要职责：

```text
登录接口放行
受保护接口鉴权
JWT 过滤器
用户身份识别
权限校验
接口访问控制
```

要求：

```text
1. 所有后台接口必须鉴权
2. 所有重要操作必须校验权限
3. 普通成员不能访问后台接口
4. 无权限时返回 403
5. 不能只依赖前端隐藏按钮
```

### 6.4 JWT

登录认证使用 JWT。

基本流程：

```text
用户提交账号密码
后端校验用户
校验成功后生成 JWT
前端保存 Token
请求接口时携带 Token
后端解析 Token 并识别用户身份
```

要求：

```text
1. JWT 密钥不能硬编码
2. Token 需要设置过期时间
3. 前端统一携带 Token
4. 后端统一解析 Token
5. 登录失败需要有基础限制
```

### 6.5 MyBatis-Plus

数据库访问使用 MyBatis-Plus。

原因：

```text
1. CRUD 开发效率高
2. 对新手更直观
3. 适合 Spring Boot 后台系统
4. 方便生成 Entity、Mapper、Service
5. 与 PostgreSQL 可以配合使用
```

注意：

```text
MyBatis-Plus 只负责数据库操作。
业务规则不要写在 Mapper 里。
复杂业务逻辑应写在 Service 层。
```

## 7. 后端架构选择

本项目不采用完整 DDD，也不采用微服务。

最终采用：

```text
模块化传统分层架构 + 少量 DDD 思想
```

含义：

```text
1. 不做复杂领域建模
2. 不做微服务拆分
3. 不做事件溯源
4. 不做复杂 CQRS
5. 但按业务模块划清代码边界
```

选择原因：

```text
1. 本人目前没有大量开发经验
2. 项目主要依赖 AI 辅助开发
3. 完整 DDD 文件和概念较多，容易增加理解成本
4. 传统分层更容易开发、测试和答辩
5. 模块化可以避免代码后期混乱
```

## 10. 分层说明

### 10.1 controller

接口层。

负责：

```text
接收 HTTP 请求
参数基础校验
调用 Service
返回统一响应
```

不应该做：

```text
复杂业务逻辑
数据库操作
复杂权限判断
```

### 10.2 service

业务层。

负责：

```text
处理业务流程
调用 Mapper
调用其他 Service
进行权限判断
进行状态流转
写入操作日志
发送站内通知
```

### 10.3 mapper

数据访问层。

负责：

```text
数据库增删改查
分页查询
条件查询
复杂 SQL 查询
```

不应该做：

```text
业务流程编排
权限判断
状态流转规则
```

### 10.4 entity

数据库实体。

要求：

```text
字段和数据库表对应
不直接返回给前端
不放复杂业务逻辑
```

### 10.5 dto

请求数据对象。

示例：

```text
LoginRequest
RegisterRequest
CreatePostRequest
UpdateNewsRequest
ReviewApprovalRequest
```

### 10.6 vo

响应数据对象。

示例：

```text
UserProfileVO
PostDetailVO
NewsListItemVO
ActivityDetailVO
AdminDashboardVO
```

## 12. PostgreSQL / OpenTenBase 兼容要求

为了后续兼容 OpenTenBase，数据库设计需要注意：

```text
1. 不使用 MySQL 专属语法
2. 不使用 MySQL 的 AUTO_INCREMENT
3. 不使用 MySQL 的反引号 `
4. 不使用 MySQL 特有字段类型
5. 尽量使用标准 SQL 和 PostgreSQL 常见写法
6. 表名和字段名使用小写下划线
7. 重要数据不要依赖数据库特定隐式行为
```

主键策略：

```text
使用 BIGINT 类型 ID
由后端生成 ID
建议使用 MyBatis-Plus 雪花 ID
```

## 13. 接口规范

后端接口统一以 `/api` 开头。

示例：

```text
/api/auth/login
/api/auth/register
/api/users/me
/api/posts
/api/news
/api/activities
/api/projects
/api/admin/users
/api/admin/approvals
```

所有接口统一返回格式：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

错误返回示例：

```json
{
  "code": 403,
  "message": "无权限访问",
  "data": null
}
```

建议业务状态码：

```text
0：成功
400：请求参数错误
401：未登录或登录过期
403：无权限
404：资源不存在
500：服务器错误
```

## 15. 权限技术方案

权限系统采用：

```text
RBAC + 权限点 + 数据范围
```

结合你目前确定的组织规则：

```text
普通成员不分部门
干事 / 副部长 / 部长绑定部门
副会长 / 会长不绑定部门
```

身份存储规则：

```text
user_roles：记录系统级身份，例如 member、vice_president、president
department_members：记录部门职务，例如组织部干事、项目部部长
role_permissions：记录角色拥有的权限和数据范围
```

后端必须提供：

```text
当前用户信息接口
当前用户权限接口
权限校验工具
后台接口权限注解或拦截器
角色等级判断
数据范围判断
```

前端负责：

```text
根据权限显示菜单
根据权限显示按钮
无权限时跳转 403 页面
```

后端负责：

```text
最终权限校验
防止越权访问
返回 401 / 403
```

## 17. 部署技术方案

第一版采用云服务器直接部署，不强制 Docker。

### 17.1 部署组成

```text
Nginx
Vue 前端静态文件
Spring Boot Jar
PostgreSQL
systemd
```

### 17.2 部署结构

```text
用户浏览器
    ↓
Nginx
    ↓
Vue 前端静态文件

用户请求 /api
    ↓
Nginx 反向代理
    ↓
Spring Boot 后端
    ↓
PostgreSQL
```

### 17.3 前端部署

前端构建：

```bash
npm install
npm run build
```

生成：

```text
dist/
```

部署到服务器目录，例如：

```text
/www/openatom-frontend
```

### 17.4 后端部署

后端构建：

```bash
mvn clean package
```

生成：

```text
target/openatom-backend.jar
```

服务器运行：

```bash
java -jar openatom-backend.jar
```

正式环境建议使用 systemd 管理服务。

### 17.5 Nginx 职责

Nginx 负责：

```text
部署前端页面
反向代理 /api
处理静态资源
处理上传文件访问
配置 HTTPS
```

路径规划：

```text
/          前端页面
/api       后端接口
/uploads   上传文件
```

本项目最终技术栈确定为：

```text
前端：
Vue 3 + TypeScript + Vite + Vue Router + Pinia + Axios + Element Plus

后端：
Spring Boot 3 + Spring Security + JWT + MyBatis-Plus + Spring Validation

数据库：
PostgreSQL

后续兼容：
OpenTenBase

模块化传统分层架构 + 少量 DDD 思想
```

```text
前端好看
后端清晰
权限安全
数据库可迁移
部署可落地
后续可维护
```
